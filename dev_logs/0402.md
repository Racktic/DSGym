## 二、SFT 数据格式转换

### 格式

LLaMA-Factory sharegpt 格式：
```json
{
  "messages": [
    {"role": "system", "content": "AIDE system prompt"},
    {"role": "user", "content": "任务描述 + Step 1 instruction"},
    {"role": "assistant", "content": "模型 response (search_state + python)"},
    {"role": "user", "content": "<information>执行结果</information>\n\nStep 2 instruction"},
    {"role": "assistant", "content": "..."},
    ...
  ],
  "meta": {
    "challenge_name": "...",
    "split": "swap",
    "run": "run1",
    "success": true,
    "final_best_score": 0.85,
    "baseline_score": 0.92,
    "num_turns": 20,
    "truncated_at_turn": 8,
    "original_num_turns": 20,
    "best_node_strategy": "best",
    "turns": [
      {"turn": 1, "phase": "draft", "score": null, "best_score": null, "model": "...", "buggy": false},
      ...
    ]
  }
}
```

### 处理步骤

1. **格式转换**：从 trajectory JSON 提取 conversation，合并连续 user messages，去掉 memory 相关内容（task_memory、cross-task memory、reference approach）
2. **筛选有 submission 的轨迹**：跳过没有成功提交的
3. **去掉无提升的轨迹**：final_best_score == baseline_score 的去掉（13 条）
4. **截断到 best score**：best score 之后的无效轮次去掉
   - **truncA**：截断到 best score 那一轮
   - **truncB**：截断到 best score + 保留 final_submission 轮

### 截断统计

| 指标 | 值 |
|---|---|
| 原始平均 messages/样本 | 38.8 |
| truncA 平均 messages/样本 | 24.2（-38%） |
| truncB 平均 messages/样本 | 26.2（-32%） |
| 平均 best score 出现在第 | 11.6 / 18.9 轮 |

### 已知问题

1. **metric 方向不一致**：10% 的 swap 轨迹中 LLM 对 best_score 的方向判断翻转（同一 task 不同 round 方向相反）
2. **hard 缺包失败**：13 个 hard task 因 executor-kaggle 缺 CV/NLP 包失败，需用 executor-mle 重跑
3. **训练数据不含 memory**：memory 的增益通过高质量轨迹隐式蒸馏进参数，模型不学习如何读 memory

## 三、Qwen3-8B SFT 模型评测（2026-04-03/04）

### 模型

- Checkpoint: `/data/fnie/LLaMA-Factory/saves/qwen3-8b-aide-v5/full/sft/checkpoint-50`
- 训练数据: `aide_v5_sft_improved_truncA.json` (344 samples, swap+hard+mledojo, memory stripped, truncated at best score)

### 评测环境搭建

**问题与解决**：

1. **共享文件系统慢导入**：NFS 上的 `.venv` import torch/vllm 要 5-10 分钟。解决：`cp -r .venv /tmp/dsgym_venv`
2. **submission_dir 相对路径 bug**：`submission_dir="./submissions"` 在 SSH 远程执行时 cwd 是 `/home/fnie`，找不到文件。修复：改为 `str(DSGYM_ROOT / "submissions")` 绝对路径
3. **vLLM V1 engine 并发 bug**：TP=8 时 `EngineCoreRequestType` 报错。解决：改用 multi-vllm（每 GPU 独立实例）或 TP=8 + max-workers=1

### multi-vllm 后端

每张 GPU 一个独立 vLLM 实例（TP=1），通过 `queue.Queue` 分发请求，支持 8 路并行推理。

**修复的 bug**：
- `_initialize_instances()` 原来用 `ThreadPoolExecutor` 并行初始化 8 个实例，但 PyTorch 的 `torch.distributed` parallel state 是进程级全局单例，并行初始化报 "already initialized"。修复：改为串行初始化
- CLI 添加 `--backend multi-vllm` 选项和默认 `max_workers=8`

**启动命令**：
```bash
# 1. 拷贝 venv 到 /tmp（避免 NFS）
ssh <node> "cp -r /data/fnie/qixin/DSGym/.venv /tmp/dsgym_venv"

# 2. 生成 8 容器 compose + 启动
cd executors && python generate_compose.py -n 8 -t "executor-kaggle:8" -m "../data/data" -s "../submissions" -e "EXECUTION_TIMEOUT=600" -o docker-compose-8.yml -c container_config_8.json
ssh <node> "sudo docker-compose -f /data/fnie/qixin/DSGym/executors/docker-compose-8.yml up -d"

# 3. 启动评测
ssh -f <node> "export PYTHONUNBUFFERED=1 && /tmp/dsgym_venv/bin/dsgym eval \
    --model /data/fnie/LLaMA-Factory/saves/qwen3-8b-aide-v5/full/sft/checkpoint-50 \
    --dataset dspredict-easy \
    --backend multi-vllm \
    --agent aide \
    --memory-version v5 \
    --best-node-strategy best \
    --memory-path <output_dir>/cross_task_memory.json \
    --num-drafts 5 --max-turns 20 --max-workers 8 \
    --output-dir <output_dir> \
    > <log_file> 2>&1"
```

**容器安全性验证**：Manager 用 `asyncio.Queue` 分配容器，原子操作，不会重复分配。multi-vllm 的 GPU queue 也是线程安全的。

### 结论

1. **8B SFT 模型整体偏弱**：平均 40th percentile，0 medal
2. **Memory 对 SFT 模型帮助不大**：两组 avg percentile 几乎相同（40% vs 41%），因为训练数据已 strip memory 内容，模型没学过利用 memory
3. **improve 阶段基本无效**：大部分 task 在 draft 阶段就拿到最好分数，improve 轮数浪费在 buggy debug 循环里
4. **提前终止**：task 平均 11-14 轮终止（max=20），原因是 env 的 `_is_done()` 在 `observations` 为空时触发 break
5. **multi-vllm 8 路并行有效**：38 task 全量评测约 1.5-2 小时（vs 串行预计 12+ 小时）

### 观察到的问题

- nomem 实验的 cross-task memory 不纯净：默认路径 `./cross_task_memory.json` 解析到 `/home/fnie/cross_task_memory.json`，包含旧实验数据
- 部分 Kaggle 提交失败（格式不对）：24 个 submission 中只有 14 个被 Kaggle 接受
- 最后几个 task 推理极慢：context 积累到 10+ 轮后，单次推理需要数分钟
