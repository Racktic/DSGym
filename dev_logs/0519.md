# 0519 — delta-update / mixed-update(飞轮)进展

从两个 update 机制的 ablation(caveat-update vs delta-update)开始,到把两者合成 mixed-update / 飞轮的全部进展。所有数字都是从 `evaluation_results/*_summary.json` 现拉的,不是凭印象。

---

## 0. 这轮要回答的问题

之前我们已有 caveat-update 这条线(把失败信号转化成挂在源 entry 上的 `scope_caveats`)。这次要做两件事:

1. **delta-update**(主流 append-bullet baseline):把同一次 source run 的轨迹丢回原 offline 抽 insight 那条 pipeline,新 insight 作为新条目 append 进 M₀ —— 跟我们造 M₀ 的方式完全一致,这是主流方法的做法。
2. **mixed-update**(飞轮):caveat + delta 不冲突,可以叠在同一份 memory 上同时用。delta 长池子,caveat 给老 entry 加边界。再加一个按轮的同竞赛过滤规则(M₀ 同竞赛 entry 不可见,delta 这轮新加的同竞赛 entry 可见,上限 max_per_task=2),实现 entry 级"M_i={1..i-1}"的飞轮 continual learning。

## 2. 召回机制的实证检查(关键发现)

跑完 gpt5.2 delta 之后,担心"delta 自任务 insight 召回率太高 → 自任务泄漏"。**实测把这个担心证伪了**:

在 gpt5.2_delta_easy_test 上扫了所有 81 个 memory block(8 题、12 轮 / 题、含 draft/improve/debug):

- **231 个召回的 insight 槽位里只有 12 条(5.2%)是 delta 新加的**,其余全是 M₀ 的老 insight
- **当前题自己在 v2 那次跑出来的 insight 一次都没被召回过**(8 个题全 0)
- 这 12 条全是题与题之间的互相召回:7 条 easy → easy(因为新 delta 含 easy v2 抽的),5 条 easy → hard(新 delta 也含 hard v2 抽的)

为什么"task 描述近乎一样、cosine ≈ 1 的同竞赛 entry 召回 0 次"?**因为 `smart_retriever.py:371` 写死了"challenge_name == 当前题就全排掉"**。也就是我们这条召回逻辑结构上就不允许自任务召回,根本不存在 leakage。

顺带把 Dynamic Cheatsheet 查实(arxiv 2504.07952):它的 M_i 也只用 {1..i-1},每题先评再写记忆,自任务不可读。DC 不避讳的只是"不同题但同分布"的近似题召回,这个我们本来就允许(跨竞赛 cosine 召回)。**所以我们这条规则和 DC 协议一致,不应该一刀切去掉**。

剩下 5.2% 的来源也清楚了:**为什么 delta 新加的 75/63 条只占召回的 5%**?action-aware 硬过滤(draft 轮只召 draft 类,新加的 87% 是 improve 类)+ domain/task_type 硬过滤 + 1223 条 M₀ 稀释 + `max_per_task=2` + 稳定池 15 取 3 随机采样。delta 的 append 在结构上就被淹没了——这是后面飞轮 framing 的重要支撑(append-only 在这种 retrieve 下是"检索饥饿"的,跟 caveat 把修正挂到本来就被高频召回的 M₀ entry 上完全不同的 economy)。

## 3. mixed-update / 飞轮

### 3.1 算法

两个 update 算子作用在同一 entry 的正交维度上,单调可叠加:

- **Δ(growth)**:把这轮新 insight 作为新 entry append 进池子。改的是"池子里有哪些 entry"。
- **Caveat(scope)**:把修正挂到出错的源 entry 上。改的是"某个 entry 何时可信"。
- 一个 Δ-新加的 entry,在下一轮就是池子里普通一员,可以被检索、可以错误泛化、于是可以被挂 caveat → entry 生命周期:**Δ 出生(未定界,高方差)→ 复用 mis-generalize → 挂 caveat(定界)→ 成熟**。

### 3.2 同竞赛过滤的按轮版本(为飞轮服务)

原规则:`challenge_name == 当前题 → 全排掉`。

飞轮需要"上一轮在这个题上学到的东西,这一轮可以读到",所以把它改成按轮:

- entry 的 `challenge_name == 当前题` **且** 来自 M₀(round_origin = 0)→ 排掉(和之前所有实验完全一致,基线干净)
- entry 的 `challenge_name == 当前题` **且** 来自更后面的轮(round_origin ≥ 1)→ **允许**
- entry 的 `challenge_name ≠ 当前题` → 跨任务召回,照常

这正好是 DC 那条 `M_i = {1..i-1}` 在 entry 级 round 粒度的对应。`max_per_task=2` 自动把这种同竞赛上一轮 entry 卡在最多 2 个,M₀ 跨任务的还是占 ≥13/15 池子。

### 3.3 实现

`dsgym/agents/vgs/smart_retriever.py` `_build_pool` 的同竞赛过滤改成 round-aware,代码里有一大段注释说明 why、怎么编码、向后兼容(没有 `round_origin` 字段的 entry 默认 0,旧 memory 文件行为不变)。

memory entry 增加一个字段:

```json
"round_origin": 0   // 来自 M₀
"round_origin": 1   // 由 round-1 的 delta 加入
```

embedding 不需要重算 —— enrich 只 embed `task_description[:3000]`,加 `round_origin`、carry `scope_caveats` 都不动这个字段,旧 npy 直接复用,顺序拼接即可。

### 4.3 跨模型综合

| | Sonnet EASY | Sonnet HARD | gpt5.2 EASY | gpt5.2 HARD |
|---|---|---|---|---|
| 最高的 | delta / mixed#2 同档 | mixed ≈ caveat > delta | **M₀** | delta |
| **mixed 是否赢两个单独 update** | 大致打平 | 打平 caveat、赢 delta | **赢两个,但输 M₀** | 没赢 |

**实话**:目前 4 个数据点里,mixed 真正"明显赢两个单独 update"的只有 **gpt5.2 EASY 这一格**(strict-common: mixed 53.6 vs delta 46.7 vs caveat 40.7)。Sonnet HARD 是"打平 caveat、赢 delta"(算半个支持点)。Sonnet EASY 单次方差太大没法判。gpt5.2 HARD 不支持。

**飞轮 framing 现在的实验支撑还不足,但有迹象**:
- gpt5.2 EASY 上 mixed 显著比单独 update 强,但还输 M₀,说明 update 机制本身在 gpt5.2 + EASY 这个组合上整体不利,mixed 在这种不利情况下至少做到"在 update 机制里最优";
- Sonnet HARD 是 mixed 表现最像飞轮预期的一格——把 caveat 这条线的优势保下来同时不被 delta 拖崩。

## 5. 这次踩出来的几个工程坑(避免重复)

1. **新跑 dsgym eval 必须传 `--manager-url`,不要靠 `DSGYM_MANAGER_URL`**——CLI 默认 `localhost:5000`,环境变量没读。
2. **SmartRetriever 需要 `LITELLM_API_KEY` + `OPENAI_API_KEY` 都设,否则 fallback 到 naive 检索**(就会出现 "enriched memory detected but $LITELLM_API_KEY unset")。直连 OpenAI 跑时 LITELLM_API_KEY 就用 OpenAI key,LITELLM_BASE_URL 设 `https://api.openai.com/v1`。
3. **reasoning 模型的 max_tokens**:OpenAI reasoning(`gpt-5`、`o-` 系列)不收 `max_tokens` 和非默认 `temperature`,要用 `max_completion_tokens` 且预算放大(reasoning token 吃配额)。`build_cross_task_memory_offline.call_summarizer` 已 patch,enrich/分类阶段绕开方法是用 `gpt-4o-mini`。
4. **Kaggle KGAT_ token 走 Bearer**:`export KAGGLE_API_TOKEN=...`,kagglesdk 自动走 Bearer,Basic auth(从 kaggle.json 读 username+key)早就 401。
5. **每跑前回收对应容器栈**:easy stack `dspredict_easy_v2`(port 5100),hard stack `dspredict_hard_v2`(port 5200),不回收容易拿到上一轮的脏状态。

## 6. 下一步候选

按当前 4 档 ladder 的数据,有几个方向可选:

1. **case 分析**:扒 gpt5.2 EASY 上 mixed 为什么显著赢 caveat/delta(那是 mixed 唯一明显赢的格子,机制级证据);以及 Sonnet HARD 上 mixed 怎么保住 caveat 的优势。
2. **为什么 update 机制在 gpt5.2 EASY 整体不如 M₀**(三个 update 都比 M₀ 低 5-20 pub),搞清楚是 retrieve 召回了误导内容还是别的原因。
3. **多轮飞轮**:目前是单轮 mixed = 1 epoch。真正的飞轮要 t=2、t=3 看 Δ 沉淀 + caveat 累积的收敛。
4. **多 seed / 多次复跑稳定性**:Sonnet EASY mix#1 vs mix#2 之间方差非常大(43.9 vs 61.8),s5e3 + titanic 都摆动 50+,需要多次平均才能给 paper 用。
5. **保留 / 调整同竞赛限额**:现在 max_per_task=2 把同竞赛上一轮 entry 卡在 ≤2/15。可以单独设"同竞赛限额 = 1 或 0",看是不是 mixed 在 HARD 上 mixed 没赢的原因之一。
