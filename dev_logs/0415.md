# 2026-04-15 Cross-Task Memory 失败机理深度分析

起因：dev_logs/0410.md 的 Collective Intelligence 实验里发现 `recruit-restaurant-visitor-forecasting` 这个 task 在 Claude + SmartMem 下 Kaggle public percentile 掉了 32.6（66.4 → 33.8），但 agent 自己报的 `final_best_score`（validation RMSLE）反而**更好**（0.517 → 0.482）。

这个 CV 与 Kaggle 打分的背离促使我们打开两条轨迹做逐轮代码对比，找到了 **memory 导致失败的真实机制**。

---

## 1. 两个 agent 的策略走向

两组都是 Claude Sonnet 4.6、12 turns、same prompt，唯一差别是 `--memory-path` + `--no-cross-memory-write`。

### NOMEM agent（没有 memory）
轨迹：`evaluation_results/claude_sonnet_nomem_hard_test/recruit-restaurant-visitor-forecasting_20260415_014039_trajectory.json`

- Turn 1-8: 尝试多个包含 lag 特征的方案，因 HPG 大表 + 复杂 merge 反复 timeout
- Turn 8: 退到 store-DOW median 的纯统计方案
- Turn 9-10: 加 LightGBM 小模型
- **Turn 11 关键诊断**：
  > "The lag features have very low coverage for the validation period (**only 18% for lag_7**)... **The real issue is that the lag features aren't helping much because of sparse coverage. Instead, I'll add air reservation features** which provide forward-looking information."
  
  → 主动**放弃 lag features**，改用**预约数据**（反向前瞻信号）
- Turn 12 final: 沿用 Turn 11 方案，训练 500 轮
- final validation RMSLE **0.517**
- Kaggle public percentile **66.4**（在 median 以上）

### +MEM agent（带 SmartMem）
轨迹：`evaluation_results/claude_sonnet_smartmem_hard_test/recruit-restaurant-visitor-forecasting_20260415_065648_trajectory.json`

12 轮注入了 12 组 cross-task memory，主要 insight 来自：
- **m5-forecasting-accuracy**: "lag-7, lag-28, roll_mean_7, roll_mean_28 capture seasonality"
- **walmart-recruiting-store-sales**: "same-week-last-year lag (lag_52, lag_104) are **the single most powerful** features"
- **web-traffic-time-series**: "day-of-week bias terms + lag"
- **playground-series-s3e19**: "CatBoost with categorical groupings"
- **LANL-Earthquake**: "time-based splits to avoid leakage"

全都是 time-series 类任务，有**非常明确的 lag-centric 信号**。

Agent 行为：
- Turn 1-8: 跟 NOMEM 类似的 timeout 探索
- Turn 10: "add LightGBM on top of aggregate stats"
- **Turn 11 关键决定**：
  > "The single most impactful improvement I can make is to add **lag features** (visitors from 7, 14, 28 days ago)... These lag features **capture recent trends and are the strongest predictors in time-series forecasting**."
  
  → 沿用 memory 的建议，**加 lag_7/14/28**，validation 从 0.484 → 0.482
- Turn 12 final: **再加 lag_21/35/42**，"because merge approach is fast enough"
- final validation RMSLE **0.482**（自我评估更好）
- Kaggle public percentile **33.8**（median 以下）

## 2. 为什么 validation 更好但 test 更差

### 根本机制：test horizon 超过 lag-k → lag features 大量 NaN

Train 数据最后一天：**2017-04-22**
Test 时段：**2017-04-23 ~ 2017-05-31**（黄金周 + 5 月全月）

对一个 test 日期 `d`，`lag_k` 要查 `(store, d - k)` 的 visitors。

| 测试日期 | lag_7 要查 | train 有吗？ |
|---|---|---|
| 2017-04-23 | 2017-04-16 | ✓ |
| 2017-04-29 | 2017-04-22 | ✓（最后一天） |
| 2017-04-30 | 2017-04-23 | ✗（test 期） |
| 2017-05-01 | 2017-04-24 | ✗ |
| ... | ... | ✗ |
| 2017-05-31 | 2017-05-24 | ✗ |

从 **2017-04-30** 起，`lag_7` 全部 NaN（train 里没有 test 之间的数据）。`lag_14/21/28/35/42` 同理，只是崩得更早或更晚。

**结果**：test 行的 lag 特征大部分为 NaN。

### LightGBM 默认 NaN 处理的二阶后果

训练数据里 NaN 只出现在：每家店**最早几天**（尚未有 k 天历史）。那些 early dates 的 visitor 数**系统性偏低**（店刚开张、客流未稳）。

LightGBM 会学习 "`lag_k` is NaN → predict low"，因为训练 NaN 样本的 target 就偏低。

**Test 上一整 month 的 lag 全是 NaN → 所有预测被系统性拉向"店面早期的低客流"**。

### 数值证据

| | NOMEM 提交 | +MEM 提交 |
|---|---|---|
| mean visitors | **20.6** | **10.8**（系统性低一半） |
| median | 17.3 | 5 |
| min | 1.09 | 0 |
| max | 103.5 | 130 |
| dtype | float | **int（强转）** |

NOMEM 分布接近合理（店均日访问 15-25），+MEM 分布被 NaN 陷阱压成一半。

### 额外的 code bug

+MEM 的 final turn 还有个独立 bug：
```python
submission['visitors'] = np.round(test_preds).astype(int)  # ← 强制取整
```
NOMEM 保留 float。对 RMSLE（log1p 空间）来说：
- 预测 0 vs 实际 10 → `(log(1) - log(11))² = 5.75`
- 预测 2 vs 实际 10 → `(log(3) - log(11))² = 1.70`
- 预测 0.4 vs 实际 10 → `(log(1.4) - log(11))² = 4.26`

取整把 0.4 变 0，大幅加重 penalty。NaN + int 取整双重打击。

## 3. 关键洞察：Memory 是 "信号"，不是 "理由"

两个 agent 的**推理路径**不同：

### NOMEM agent 从第一性原理走
1. 试 lag features
2. 测量 validation 覆盖率 → "18% for lag_7"
3. 识别这是本质问题（不是实现问题）
4. **放弃 lag → 换预约数据**

### +MEM agent 被 memory 授权略过了诊断
1. 试 lag features
2. 看到 memory 里 walmart/M5/web-traffic 都说 lag 是"最重要"
3. **跳过"lag 是否适合当前 task"的检验**
4. 扩大 lag 范围 (7/14/21/28/35/42) 以"利用 insight"

**Memory 传递的是 "有效模式"，但没传 "适用边界"**：
- Walmart entry 说 "lag_52 最强" → **不提 "forecast horizon 至少 52 周"**
- M5 entry 说 "lag_7/28 + recursive forecasting" → **不说 "必须 recursive 更新 lag"**
- Web-traffic entry 说 "day-of-week bias + lag" → **不说 "适用 multi-year history"**

Recruit-restaurant 是：**15-30 天 direct forecast**，非 recursive，lag 在 test 期大量 NaN。memory 里**没一条 insight 带 "不适用条件"**。

---

## 4. 这是 imitation-without-understanding 失败模式

`+MEM agent` 把 memory 当**权威指导**（而非**参考候选**），因此：
- 关掉了自己基于 validation 覆盖率的诊断能力
- 放弃了 "换思路"（reservation features）的机会
- 沿用一个在源任务 work、在当前 task 不 work 的 trick

NOMEM agent 没有 memory 信号"噪音"，依靠 evidence-based diagnosis 做出了正确决定。

这个 case 提供了一个**反直觉结论**：对已经强的 agent（teacher 级），**naive memory injection 可能降低其批判性推理能力**。

## 5. 对 Selective Memory / 下一代 Retriever 的启示

### 当前 SmartRetriever 的问题

仅基于 task_description embedding 做相似度召回。对于 recruit-restaurant：
- 匹配到的 memory 都是 "time-series forecasting" 类 → task similarity 高
- 但没有匹配"适用条件"：recursive vs direct、forecast horizon、lag 可用性

### 改进方向（按 effort 排序）

**A. 快速修补：给 memory entry 加 scope metadata**（1-2 天）

重跑 `scripts/build_cross_task_memory_offline.py`，在 Claude summarizer prompt 里要求输出额外字段：
```json
{
  "insight": "lag_52 features are most powerful",
  "applicable_when": "forecast horizon >= 52 weeks AND multi-year training data",
  "not_applicable_when": "short-range forecasting without recursive updates"
}
```

Retrieve 时把 `applicable_when` 也贴进 prompt，让 agent 自己判断是否适用。

**B. 中等 effort：prompt-level caveat**（0.5 天）

改 `smart_retriever.py format_for_prompt`，在 memory block 末尾加固定提醒：

```
=== END CROSS-TASK MEMORY ===

Note: These insights are from OTHER tasks. Validate applicability to the CURRENT task
before adopting. Specifically check: (1) data distribution match, (2) feature availability
at test time, (3) whether the source task's validation setup resembles yours.
```

这对 teacher 级 agent 足够，因为它们 reasoning 能力强，一旦 prompt 明说就会做检验。对学生模型可能无效。

**C. 大 effort：query-time applicability check**（2-3 天）

Retrieve → 让 Claude 用 current task + memory entry 判断"适不适用"，过滤/打分：
```
current_task: {full desc of recruit-restaurant}
candidate_insight: {walmart lag_52 insight}
→ "Walmart has multi-year data; recruit-restaurant has <18 months. Test horizon
  longer than most lag values → lag features will be NaN-heavy. NOT APPLICABLE."
```

只保留 applicable 的注入。等于用 LLM 在 retrieve 时做 soft filter。

**D. Radical：只给同 domain + 同 evaluation setup 的 memory**（需要 metadata 重构）

扩展 `enrich_memory_metadata.py`，除了 `domain`/`task_type`/`metric`，再加：
- `eval_setup`: "recursive_forecasting" | "direct_forecasting" | "static_ml" | ...
- `horizon_days`: int or None
- `train_test_distribution`: "iid" | "temporal_split" | "distribution_shift"

hard filter 要求这些匹配，而不只是 domain 匹配。

## 6. 给 collective intelligence 实验的修正

之前在 0410.md 说 "memory 害 time-series / sequence 任务"。现在更准确：

> Memory 不是对 time-series 本身有害，而是**当 memory 里的 insight 隐含了源任务特定的 eval setup（recursive forecasting、long history、contiguous validation）**时，搬到 multi-step direct forecasting + short history 的任务上会导致系统性 bias。

这不是 time-series 的**固有问题**，是 memory representation 缺少 applicability scope 的问题。

## 7. 第二个 case 研究：store-sales-time-series-forecasting

同一 memtest 实验里另一个 memory 害惨的 task，机制**跟 recruit-restaurant 不同，但 root cause 一致**（memory 的 lag insight 没带 scope）。

### 数据速查

| | Agent Val RMSLE | Kaggle Test RMSLE | Val→Test Drift | Kaggle pct |
|---|---|---|---|---|
| NOMEM | 0.476 | **0.468** | +0.008（几乎零漂） | **68.5** |
| +MEM  | **0.378** | 0.534 | **-0.156（炸裂）** | 42.4 |

Agent 在 +MEM 下自认为做到了 CV RMSLE 0.378（比 NOMEM 的 0.476 好 20%），实际 Kaggle 分更差 14%。

### +MEM 策略（sophisticated）
Memory 注入 M5 / Walmart / Web-traffic 的 lag + recursive 模式：
- Short lags: `lag_1, lag_2, 7, 14, 28`
- YoY lags: `lag_364, 365, 371`
- Rolling mean/std: `roll_7/14/28`
- LightGBM 1000 轮
- **Recursive 15-day forecasting**：对每个 test 日期，从 `hist` 查 lag → predict → 把预测 append 到 `hist` 给下一天用

Feature importance: `day` (5272) → `lag_1` (5268) → `dcoilwtico` → `family_code` → `dayofweek` → `lag_7` (3671)。**lag_1 是第 2 重要**。

### NOMEM 策略（static）
无 memory 信号，agent 因 LightGBM 反复 timeout 转向**纯统计聚合**：
- Store×family×DOW median
- Trend multiplier (近 2 周 / 前 4 周)
- Promo multiplier
- **Same-week-last-year lookup**（agent 自己想出来的 YoY 信号，alpha=0.4 blend）

所有特征都在 train 上 fit 一次，test 直接 lookup——**没有自回归**。

### 失败机制：validation 机制 ≠ test 机制

**+MEM validation**（假的 recursive）：
```
val 日 Aug 15: lag_1 = Aug 14 的真实 sales
→ 验证 RMSLE 0.378
```

**+MEM test**（真的 recursive）：
```
Aug 16: lag_1 = Aug 15 真实值 ✓
Aug 17: lag_1 = 模型在 Aug 16 的预测值
Aug 18: lag_1 = 模型在 Aug 17 的预测值（用 Aug 16 的预测作 lag）
...
Aug 31: lag_1 经过 15 跳自回归链
```

模型**第 2 重要**的特征在 test 上 14/15 的行都是自己预测的值，误差指数累积。

**NOMEM 无此问题**：所有特征 train-test 同函数计算（静态 lookup），所以 val 0.476 ≈ test 0.468。

### 跟 recruit-restaurant 对比

| | recruit-restaurant | store-sales |
|---|---|---|
| 模型类型 | LightGBM + 静态 lag | LightGBM + **recursive** lag |
| Lag 在 test 上的问题 | 大量 **NaN**（forecast horizon > lag_k） | 自我预测链 **误差累积** |
| 症状 | submitted mean = 真值的一半 | submitted 分布正常，但 Kaggle RMSLE 40% 劣化 |
| Memory 缺的 scope | "lag_k 要求 forecast horizon ≤ k" | "recursive 必须用 recursive 验证" |

两个 case 的根因都是 **memory 传了 "lag feature 有用"，但没传 "lag 的适用边界 / 验证方法"**。breaking mode 不同，故事相同。

### +MEM agent 自己还漏了一个 sanity check

Agent 在 final_submission turn 说：
> "The best model so far is Step 11 with RMSLE=0.377601... I'll use this exact configuration for the final submission"

但它**没验证过 recursive pipeline 的真实表现**。一个完整的 time-series forecasting agent 应该：
1. Val split 也用 recursive mechanism（模拟 test 的 rollout）
2. 观察 val-rolling RMSLE vs val-direct RMSLE 的 gap
3. 如果 rolling 显著更差，说明模型过度依赖短 lag，应降权

Memory 没引导 agent 做这个 check（M5 memory entry 里提到了 recursive 但没说"必须 recursive validate"）。

### 结论

`store-sales` 比 `recruit-restaurant` 更 subtle——+MEM agent 做对了 M5 推荐的 recursive 框架，但**漏了配套的验证方法**。memory 给的是"食谱"，不是"怎么检验食谱"。

这对 retriever 改进的启发：memory entry 里的 insight 不只要带 "why it worked"，还要带 **"how to verify it works in your case"**（e.g., "validate with the same prediction mechanism as test"）。

## 8. 第三个 case：novozymes-enzyme-stability-prediction（不同 failure mode）

前两个 case（recruit / store-sales）是 **memory 的 insight 对口但没带 scope**。Novozymes 是**完全不同的 failure mode：memory 与任务 domain 严重不匹配 + token 预算被 memory 挤爆 → 代码大规模 truncation**。

### 关键数据

| | Agent Val | Kaggle Pub | Kaggle Priv |
|---|---|---|---|
| NOMEM | Spearman 0.617 | **0.069** (pct 24.5) | 0.036 (pct 20.3) |
| +MEM  | Spearman 0.600 | **-0.024** (pct 4.5) | -0.036 (pct 7.4) |

**+MEM 在 Kaggle 上 Spearman 变负**（预测顺序跟真值**反相关**，比随机还差）。Public percentile 掉 20 个点。

### 根本原因：9/12 turns 代码被 token 截断

| Turn | raw_len | `<python>`/`</python>` | exec_output | Status |
|---|---|---|---|---|
| 1 | 11550 | 6/5 | 2154 | ✅ 跑了 |
| 2 | 8294 | 1/1 | 1058 | ✅ |
| **3** | 10788 | **1/0** | **0** | ❌ 截断 |
| **4** | 9904 | 1/0 | 0 | ❌ |
| **5** | 9942 | 1/0 | 0 | ❌ |
| **6** | 9924 | 1/0 | 0 | ❌ |
| 7 | 9833 | 1/1 | 600 | ✅ **唯一写 submission 的关键 turn** |
| 8 | 3205 | 1/1 | 664 | ✅（只分析） |
| **9** | 10523 | 1/0 | 0 | ❌ |
| **10** | 7713 | 1/0 | 0 | ❌ |
| **11** | 8632 | 1/0 | 0 | ❌ |
| **12** | 8502 | 1/0 | 0 | ❌（final_submission 失败） |

**Kaggle 真正提交的是 turn 7 那个弱 baseline**——它的 test 预测范围只有 52-56°C（agent 在 turn 8 自己吐槽过："very narrow range... mutation features have little weight"）。后续所有改进尝试全部被 truncation 吃掉。

NOMEM 在同样 `max_tokens=4096` 下所有 12 turns 都跑了，因为 NOMEM 的代码更简单（没有 memory 推动的"加更多 feature / 多个模型"）。

### 为什么 +MEM 的 token 预算爆了

1. **Memory block 本身吃 context**：每轮注入 2-3K chars
2. **Memory 的 insight 方向全是"更多复杂度"**：
   - santander: row-level sparse stats (6 features)
   - LANL: multi-scale sub-window features + trend
   - champs: atom-type nearest-neighbor distances (10 features)
   - loan-default: LightGBM + SelectKBest + CatBoost ensemble
   - open-problems: TruncatedSVD k=256 compression
3. **Agent 按 memory 建议扩大 feature set**：mutation delta + BLOSUM62 + position encoding + physicochemical + neighborhood context ... 代码越写越长
4. **Output 超 4096 tokens → `</python>` 切掉** → env 提取失败

NOMEM 保持了简单的 feature set（只做 mutation delta + sample_weight），output 稳稳在限额内。

### 更深层的问题：memory domain mismatch

Novozymes 是 **protein thermostability prediction + 巨大 train/test distribution shift**：
- Train: FireProtDB 29K 个**多样化蛋白质**
- Test: **~2413 个单点突变**的**同一个野生型酶**（长度 221 AA）
- Metric: Spearman 相关系数

真正需要的 domain-specific knowledge：
- ESM / ProteinMPNN 预训练蛋白语言模型
- Rosetta / FoldX ddG 物理建模
- MSA conservation scores
- 野生型结构 + 突变效应预测器

**我们的 memory bank 里零条相关 insight**——teacher distill 阶段没跑任何 protein stability / mutation effect task。retrieval 基于 task_description embedding 匹配，但匹到的 `stanford-covid-vaccine`（RNA）、`champs-scalar-coupling`（分子）、`open-problems-single-cell`（基因组学）的 insight（char n-grams、atom distances、TruncatedSVD）**对蛋白质稳定性完全无关**。

更常被匹中的是 generic tabular tasks（`playground-series-*`, `santander`, `loan-default`）——只因 task_type 都是 "regression"。

### 三个 case 的 failure taxonomy

| | recruit-restaurant | store-sales | novozymes |
|---|---|---|---|
| Memory 跟 task 的关系 | **对口但缺 scope** | 对口但缺 scope | **完全 off-topic** |
| Breaking mechanism | lag 在 test 大量 NaN | recursive 误差累积 | **token 预算爆 → 9/12 代码 truncate** |
| 是 insight 质量问题还是 memory 的 overhead 问题？ | 质量（scope 缺失） | 质量（scope 缺失） | **质量（irrelevant）+ 数量（context 占用）** |
| 主要症状 | submit 值系统性偏低 | val 0.378 → Kaggle 0.534 | 预测 Spearman 转负 |
| Kaggle 损失 | -32.6 pct | -26.1 pct | -20 pct（转负关联） |

### 给 retriever 改进的新启示

**当 memory 跟当前 task domain 不匹配时，应该少注入或不注入**。当前 SmartRetriever 无条件注入 top-5，domain mismatch 时会：
1. 浪费 context（token 预算）
2. 引入 "add more features" 这类 generic advice 的 systematic bias
3. 导致 agent 代码膨胀 → truncation

可能的防御：
- **召回阶段加 similarity threshold**：如果 top-1 cosine < 0.5，不注入（"no comparable experience found"）
- **domain match score**：`domain + task_type + metric` 至少 2/3 match 才注入
- **专门 mark "no memory" 回答**：让 agent 知道 "this task is novel to the memory bank，rely on your base knowledge"

对 novozymes 这种 domain 完全不在 memory bank 里的任务，**不注入 memory** 可能比注入 5 条无关 memory 效果更好。

## 9. 正向 case：digit-recognizer（memory 让 Claude 从 pct 12.7 → 96.5）

前三个都是 memory **负向**的 case。digit-recognizer 是整个 hard_test 里 memory 带来最大正 gain（+83.8 pct）的任务，分析它能找出 memory 起作用的条件。

### 关键数据

| | Agent Val | Kaggle Pub score | Kaggle pct |
|---|---|---|---|
| NOMEM | 0.9986 | **0.9566** | **12.7** |
| +MEM  | 0.9983 | **0.9969** | **96.5** |

Agent 自评 val 基本一致（99.8%），但 Kaggle 差 4 pp（约 1200 个样本判断不同）。**+MEM 进入了 Top 5%，NOMEM 在 Bottom 13%**。

### 两边实际提交的都是 turn 10 的代码

两边都有同样的 truncation 模式：
- Turn 11/12 `</python>` 缺失（超 token），没执行
- Kaggle submission 来自 turn 10（最后一次成功执行的 improve）
- Turn 10 两边都"retrain on full 42k + TTA"

所以决定胜负的是 **turn 10 的模型架构 + 训练配方**。

### +MEM 的 memory 内容（domain 高度对口）

Memory 12 个 block 里召回的 tasks 几乎全是 **image classification**：

| Task | 核心 insight |
|---|---|
| **plant-seedlings-classification** | **4-way TTA (horiz + vert + both flips) 提升 F1 +0.006** |
| plant-seedlings-classification | 2-way TTA horizontal flip 提升 +0.002 |
| the-nature-conservancy-fisheries | **加宽 CNN (32→64→128) + RandomHorizontalFlip + 更多 epoch** |
| sp-society-camera-model | DCT block features, LightGBM 配置 |
| pku-autonomous-driving | 6DOF CNN dual-head |
| imaterialist-furniture-2018 | HashingVectorizer 配置 |

这些是"**competitive image classification 的标准配方**"：TTA、宽 CNN、强增强、较长训练。对 MNIST 完全对口。

### 两个 agent turn 10 的具体做法

**+MEM turn 10**（SE-ResNet 风格）：
- Architecture: **64→128→256→512 channels, SE blocks, BN, dropout, skip connections**
- OneCycleLR scheduler, **60 epochs**
- RandomAffine（旋转±15 / 平移10% / 缩放0.9-1.1 / shear 5）
- **10-pose TTA**（rotation / translation / scale 组合）
- Val (with TTA): 0.9983

**NOMEM turn 10**（ResBlock + Mixup + SWA）：
- ~1.5M params CNN（比 +MEM 小）
- **Mixup** augmentation + **SWA (Stochastic Weight Averaging)** from epoch 20
- Cosine annealing
- Phase 2: "retrain on all 42k with SWA"，**val 强制 = 1.000**（val leak，无法判断）
- Phase 3: 15-pass TTA

### 为什么 +MEM 的 Kaggle 强

Memory 为 +MEM 提供了 **"MNIST 标准配方 cheat sheet"**：
1. **SE 注意力 + 更深更宽**（512 通道）—— 来自 nature-fisheries 的"宽 CNN"启发
2. **OneCycleLR** —— 比 Cosine annealing 更稳的 LR schedule
3. **标准 Affine augmentation** —— 来自 plant-seedlings 的 flip 启发推广到 affine
4. **10-pose TTA 具体 recipe** —— 直接来自 plant-seedlings 的 "4-way flip TTA" 扩展

NOMEM 的创意（Mixup + SWA）是**高级 CV 技巧**，适用于困难数据集（CIFAR-100 / ImageNet），但在清洁的 MNIST 上**反而有副作用**：
- Mixup 把清晰的数字混成模糊 blend，学习信号变差
- SWA averaging 在 train loss 已经很低时没增益
- 两者叠加 + val-leak 无法识别问题 → 模型在 test 上弱 4pp

### 为什么 memory 这次 work

对比 novozymes 的 contrast：

| | digit-recognizer | novozymes |
|---|---|---|
| Memory 找到的 tasks | ✅ **全是 image classification** | ❌ 大部分 generic tabular |
| Insight 的具体性 | ✅ "4-way flip TTA +0.006" 具体数字 | 模糊 "sparse stats, multi-scale" |
| 可直接 transfer | ✅ MNIST 就是 image classification | 蛋白稳定性 ≠ tabular |
| Memory 对 agent 的 net effect | 推向"标准 CV 配方"（稳、具体、对口） | 推向"加更多 feature"（token 爆 + 乱方向） |

### 归纳：memory 有效性的 2 个条件

1. **Retrieval domain-matched**：top-K memory 里的任务必须跟当前 task 在 domain/task_type/evaluation 上高度对口。digit-recognizer 的 top-3 全是 CV 图像分类；novozymes 的 top-3 全是 generic tabular。
2. **Insight specificity**：memory entry 必须带**具体数字 + 具体代码片段**（"4-way TTA improved F1 by +0.006", "learning_rate=0.03, num_leaves=31"），不是 vague advice。

两个条件同时满足 → memory 传递的是**别人的 battle-tested recipe**，agent 直接复用。

两个条件之一不满足：
- Only (1) without (2): memory 知道你是什么 domain 但没具体 recipe → 不如 agent 自己想
- Only (2) without (1): memory 有具体 recipe 但是别的 domain 的 → 乱施肥

### 对 retriever 改进的进一步启示

之前两个 case 说"加 similarity threshold / domain match score"。digit-recognizer 的正向 case 补充了：
- **retrieval 要兼顾 specificity**：优先召回有 "quantitative improvement"（如 "+0.006"）和 "concrete code pattern"（如 "learning_rate=0.03"）的 entries
- **建议在 enrich_memory_metadata.py 里再加一个字段 `specificity_score`**，用 Claude 判断 insight 是否"具体可执行"（带数字、带代码、带 API），retrieve 时加权
- **dual goal**: (a) 去掉 novozymes 这种完全 off-topic 的 noise，(b) 保留 digit-recognizer 这种具体对口的 gold

## 10. home-data-for-ml-course 正向 case（+97 pct，涨幅最大）

### 10.1 现象

| 版本 | final_best_score (CV RMSLE) | Kaggle public | pct |
|------|------------------------------|---------------|-----|
| NOMEM | 0.12038 | MAE = 36474.23 | 1.36 |
| +MEM  | 0.11750 | MAE = 13163.36 | 98.34 |

**CV 分数几乎一样（差 0.003），Kaggle MAE 却差了 2.77x**。这比 digit-recognizer 更反常：digit 是 +MEM 的 CV 就明显更好（0.9979 vs ~0.97），这里是 CV 基本平手但 test 天差地别。说明这个 task 的主要 delta 不来自"memory 给了更好的模型配方"，而来自另一个机制。

### 10.2 Task description 有坑：metric 标注错误

- Task 描述 (challenge_description) 明说 metric = **RMSLE** (RMSE of log predicted vs log observed)
- Kaggle 实际 public leaderboard 给的是 **MAE**（从 score 数值 36474 / 13163 美元规模可知，绝不可能是 RMSLE）
- 两个 agent 都按 RMSLE 训练，都没发现这个不一致 → 这就解释了为什么 CV RMSLE 相近但 Kaggle MAE 差这么多：**MAE 对于"幅度错得离谱的样本"比 RMSLE 更敏感**（RMSLE 取 log 后压缩了大数）

### 10.3 真正的 root cause：NOMEM 最后一次实际执行的 turn 把 submission.csv 写坏了

这是最关键的发现。两边都是 12 turns（turn 0-2 draft, 3-10 improve, 11 final_submission），并且 **turn 11 在两边都 exec_len=0**（AIDE 的 final_submission phase 只产代码不执行）。所以 Kaggle 拿到的 submission.csv 是**最后一次实际 exec 的 improve turn 写的那个文件**。

| turn | NOMEM closed? | NOMEM exec? | NOMEM CV | +MEM closed? | +MEM exec? | +MEM CV |
|------|---------------|-------------|----------|--------------|------------|---------|
| 0    | yes           | yes         | 0.133    | yes          | yes        | 0.138   |
| 1    | yes           | yes         | 0.138    | yes          | yes        | -       |
| 2    | yes           | yes         | 0.130    | yes          | yes        | 0.140   |
| 3    | yes           | yes         | 0.125    | yes          | yes        | 0.133   |
| 4    | **NO**        | **0**       | (truncated) | yes        | yes        | 0.124   |
| 5    | **NO**        | **0**       | (truncated) | yes        | yes        | 0.128   |
| 6    | **NO**        | **0**       | (truncated) | yes        | yes        | 0.122   |
| 7    | **NO**        | **0**       | (truncated) | yes        | yes        | 0.124   |
| 8    | yes           | yes         | 0.128    | yes          | yes        | 0.127   |
| 9    | yes           | yes         | 0.125    | yes          | yes        | 0.125   |
| 10   | yes           | yes         | **0.530**💥 | yes       | yes        | **0.118** ✓ |
| 11   | yes (final)   | no          | -        | yes (final) | no         | -        |

- **NOMEM turn 10 CV = 0.530**（5-fold: 0.33 / 0.67 / 0.55 / 0.60 / 0.49），基本是 raw SalePrice vs log(SalePrice) 的转换错误或 best_iter=2974+/3000 严重 overfitting。采样看 submission：Id=1462 SalePrice = **$52,578**（邻近房子都在 $160k 附近）—— 预测崩了。
- **+MEM turn 10 CV = 0.118**，这是全局最好的一次，写入的 submission.csv 完全正常（Id=1462 SalePrice = $159,942）。

结果：Kaggle 拿到的 NOMEM 文件是一个**被崩掉的 turn 10 污染的 CSV**；拿到的 +MEM 文件是 agent **整个 trajectory 里最稳的一次**。这才是 +97 pct 的真实来源。

### 10.4 为什么 NOMEM 没能把 turn 10 的灾难救回来？—— 4 个 turn 被 truncation 吃掉

- NOMEM turn 4-7：raw_response = 9172~9465 chars，`</python>` 标签**没闭合**，exec_len=0。这是命中了 `max_tokens=4096` 的输出 cap。
- NOMEM 的 improve phase 原本有 8 个 turn（3-10），实际只有 4 个（3, 8, 9, 10）跑通 —— 一半的算力被输出截断吞了。
- +MEM 的所有 improve turn 都 close 了 `</python>`，raw_response 稳定在 7200-8783 chars（比 NOMEM 小 1-2k）。memory 给了具体配方 → 代码更紧凑 → 不超预算。

**这是 writeeveryturn + max_tokens=4096 组合 in the wild 的典型失败**：agent 每个 turn 都要写完整 submission.csv pipeline，一旦没 memory 的帮助，pipeline 代码量就会飙到 4k+ token 频繁被截，等到最后 turn 10 崩了也没机会再迭代回去。

### 10.5 Memory 提供了什么

+MEM turn 0 收到的 3 条 cross-task memory：

1. `playground-series-s4e5`（flood prob regression）— HistGBR + lr=0.05 + 800 iter + 去掉 RobustScaler
2. `ashrae-energy-prediction` — LightGBM，RMSLE=1.217 ⚠️（警示性 case，说它 validation 太差可能是 merge 出错）
3. `liberty-mutual-property-inspection` — XGBoost + label encoding + grid search on `n_estimators/max_depth/learning_rate/subsample`

**第 3 条是决定性的**：它给了一个精确的 "tabular regression → XGBoost + label-encode + tune 几个关键 hyperparams" recipe。MEM agent turn 0 的 `<goal>` 里第一句话就是 "I'll build a gradient boosting model (XGBoost) for the Ames Housing" —— 完全照搬。最终 turn 11 配置就是 `XGBoost, n_estimators=3000, lr=0.02, max_depth=5, subsample=0.8, colsample_bytree=0.8, early_stopping_rounds=100`，classic shrinkage + more trees + early stopping 配方。

NOMEM 则在 draft 3 里都在探索不同模型（turn 0-2 是 xgb/lgbm/ridge 之类 baseline，turn 3 开始 CatBoost），没有一个明确的北极星，turn 10 还在试新的 CatBoost 配置结果写崩了。

### 10.6 新的失败模式刻画

home-data 这个 case 不属于前面总结的 3 种（scope-missing / domain-mismatched / 纯正向）。它更像一个**正向 + writeeveryturn trap 叠加**的混合：

> **"disk-clobbering" 模式**：writeeveryturn 要求每个 turn 都写 submission.csv，没有 memory 的 agent 因为 token 预算紧张被迫跑更长的代码，反而更容易：
>   - (a) turn-level truncation（4-7 全截）
>   - (b) 在残留的少数执行 turn 里 desperate 尝试变体，其中一次崩掉后没机会恢复
>   - (c) 最终被"最后一次执行"这个机制钉在崩掉的状态上

Memory 在这里的贡献不是"教会 agent 怎么建模"（NOMEM 也会建），而是：
1. **缩短代码长度** → 规避 4096-token truncation
2. **提前锁定配方** → 避免在后期（turn 10）乱试新配置写坏 submission.csv
3. **稳定每个 improve turn 的产出** → writeeveryturn 机制下"最后一次执行"就是最稳的那次

### 10.7 对 system 改进的启示

这个 case 给 writeeveryturn 设计提了一个补丁需求：

- **应该在每个 turn 存 submission.csv 时带 CV score**，final 阶段选"历史上 CV 最好的那个 turn 的 submission.csv"提交，而不是隐式地用"最后一次 exec 的产物"。
- 或者：如果 AIDE 认为某个 turn 的 CV 比历史 best 差很多（比如差 2x+），就**不要让它 overwrite disk 上的 submission.csv**。
- 这比改 retriever 更紧急——因为 home-data 的崩盘完全是**机制问题**，跟 memory 质量无关。

同时也印证了：memory 的价值不只在"教知识"，还在"让模型紧凑" —— 这是之前没观察到的 second-order effect。

### 10.8 回头看 metric 标注问题

Kaggle 实际用 MAE，task 描述写 RMSLE —— 这是 DSGym bench 的一个 data quality bug。理论上应该修 task description 或者至少警告：

- 如果 challenge desc 和 Kaggle 实际 metric 不一致，会严重干扰 per-task 结论的可解释性
- 建议开一个单独的 `task_metric_audit.md`，用 `kaggle api competitions get` 拉 ground truth metric 核对全部 hard_test + easy_test，写回 bench spec

### 12.2 路径 A — Similarity threshold（轻量、快速验证）

步骤：
1. 在 `SmartRetriever.retrieve()` 加一个 debug dump：每次召回写 `(challenge_name, action, retrieved_cnames, cosine_values)` 到 `logs/retrieval_debug.jsonl`（~15 行改动）
2. 跑一轮 `hard_test` + `easy_test`，采满所有任务的召回 cosine 分布
3. 离线分析 6 个已知 case 的 cosine：
   - 负样本：recruit-restaurant、store-sales、novozymes（+MEM 伤）
   - 正样本：digit-recognizer、home-data-for-ml-course（+MEM 赚）
   - 中性：随机抽 1 个平的
4. 如果负 case 的 cosine 明显低于正 case，就取分界线做 threshold；低于 threshold 返回空 pool → agent fallback 到 no-memory 行为

产出：一个具体的 threshold 值 + 实验曲线，预期能消掉 novozymes 型故障。

### 12.3 路径 B — Group Continual Learning（更 novel、主打方向）

把 memory 从"positive experience one-way 积累"变成"从集体失败反向修正的 closed-loop"。类比：RLHF 用 reject 信号改 policy → 这里用 per-task delta 改 memory。

Pipeline：

```
collective memory v_k
   │
   │ (eval on hard_test / easy_test)
   ▼
per-task delta = pct(+mem) - pct(no-mem)
   │
   │ (挑 delta < -ε 的 "memory-hurt" cases)
   ▼
Critic LLM 输入: (task_desc, 被召回的 memory entries, +mem trajectory, no-mem trajectory)
   │ 输出: {root_cause, which_entry_hurt, proposed_patch}
   │        patch 可能是：
   │          • 给 entry.insight 追加 scope condition
   │            （如 recruit-restaurant 的 "lag features 不能长于预测 horizon"、
   │              store-sales 的 "recursive forecasting 会累积误差"）
   │          • 标记 entry 为 "penalty" 让 retriever 扣分
   │          • 删除纯误导性 entry
   ▼
collective memory v_{k+1}
   │
   │ (re-eval)
   ▼
验证 delta 曲线是否从负转正
```

关键设计点（待研）：
- Critic prompt：怎么让它稳定 localize 到"哪条 entry 害人" + "insight 缺什么 scope"
- Memory patch schema：`insight` 字段追加 `scope_caveats` 子字段，还是直接改写？
- 迭代终止条件：max iterations / 所有 memory-hurt < ε / delta 不再上升

为什么 novel：
- 不是 "retrieve-better" 的 engineering trick，而是 memory 作为一个会**自我修正的集体认知**
- 每轮都有量化指标（memory-hurt case 数 ↓、平均 delta ↑）可以画曲线做 paper figure
- 和 path A 正交：A 挡"根本不该召回的"，B 修"召回了但害人的"

### 12.4 实施顺序

1. **先 A**（1-2 天）：retrieval debug dump → 采数 → 定 threshold → 上线验证
   - 产出的 cosine 数据同时也能喂给 B 的 critic（知道"哪些 entry 以低相似度被强召回"）
2. **再 B**（~1 周）：critic prompt 设计 → patch schema → 跑 v_1 re-eval → 看 delta 曲线
3. B 跑通后，考虑合并 A + B：threshold 本身也可以是 continual learning 的一个可调超参
