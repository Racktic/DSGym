**交互效应**：
- 单 prompt 加不上 valid rate（模型听 "每轮写 submission" 指令，但代码还是崩在 `to_csv` 之前）
- 单 memory 提升 percentile 很多但 valid rate 只微涨
- **两者组合 valid rate 跳到 75%**：memory 让代码更可能跑通 → prompt 的 "每轮写" 才真正生效
- trade-off：combo 多出的 3 个 valid 都是"勉强跑通 + 分数平庸"的 task，所以 avg percentile 从 60.6 降到 22.0

## 4. 核心发现

1. **SmartMem 对 percentile 提升显著**：
   - Easy public 32.6 → **60.6**（+28 pts），接近甚至略超 teacher 均值
   - Hard public 0 → **41.5**（从完全 fail 救到 teacher 水平）
   - 但 valid rate 只微弱提升（2/8 → 3/8，0/10 → 2/10）

2. **SFT 有害 vs memory 友好**：
   - SFT v4 在 easy 上 0/8 valid（比 baseline 2/8 还差），在 hard 上 3/10 valid（比 baseline 0/10 好）
   - 说明 SFT 教会了 hard 类 task 的 pipeline，但把 easy 的格式能力搞坏了
   - 加 cross-task memory 能救回一些

3. **失败瓶颈不在策略，在代码崩溃**：
   - baseline Qwen3-8B 绝大多数 fail 都是代码 runtime error（sklearn API 幻觉、preprocessing drop 掉 target、`n_samples=0` 等），崩在 `to_csv('/submission/submission.csv')` 之前
   - memory 帮助了"写什么代码"（用 CatBoost/XGBoost/LightGBM 替代弱 sklearn），但救不了"代码执行崩溃"
   - 单跑 writeeveryturn prompt：模型 follow prompt（20/20 都写 submission 路径），但还是崩在 to_csv 之前 → valid rate 没变
   - **SmartMem + writeeveryturn 组合才真正 unlock**：memory 先保证代码跑得通，prompt 再保证末尾写 submission → valid rate 从 25% 跳到 75%

4. **ceiling 天花板**：Qwen3-235B teacher 在 easy 上 valid rate 5/8、avg %ile 58.8。**Qwen3-8B + SmartMem 已经 60.6** —— 说明 memory 基本抹平 8B → 235B 的 scale gap（在 valid 的任务内）

5. **final_submission prompt 的 bug**：`AIDE_FINAL_SUBMISSION_INSTRUCTION` 只传 memory_section（文字 summary），**没传 best turn 完整代码**。模型得从 summary 重建 pipeline，常常重现漏掉关键步骤（如 LabelEncoder 在 combined 数据上 fit）导致 final 崩。

### Collective Intelligence 的真实规律

不是简单的 "memory 对 teacher 有用 / 没用"，而是 **task-type dependency**：

- **Memory 帮 tabular / classical ML 类**（digit-recognizer, home-data, spaceship-titanic, ieee-fraud）—— cross-task insight（"用 CatBoost 处理 categorical"、"加 KFold CV" 等）跟这些任务完全对口
- **Memory 害 time-series / sequence 类**（recruit-restaurant-visitor, store-sales, ventilator-pressure, novozymes-enzyme-stability）—— memory 里的 static ML trick 误导 teacher 远离领域合适解法

### Public/Private gap 解释

- 我们的 agent **只提交 1 次**，不会"过拟合 public LB"
- private 普遍比 public 差（Claude -12.2, Gemini -12.8）**不是 overfitting**
- 真实原因：**private-covered 的 5 个 hard task 里 3-4 个是 time-series / sequence 类**，恰好是 memory 的弱项；public 额外包含 digit-recognizer + home-data 这两个 memory 巨赢的 task
- 所以 gap 不是信号，是 task coverage 的 artifact

### 重要 outcome

- **Claude + SmartMem hard 拿到 🥈 2 silver**（裸 Claude 拿 0 奖）——首次验证 cross-task memory 能让 teacher 突破自身 ceiling
- Gemini 维持 🥉 1 bronze
- Teacher 加 memory **在 easy 上整体负向**（easy 对 teacher 已经简单，memory 反而稀释）

### ⚠️ 方法论注意：trajectory `final_best_score` ≠ Kaggle score

Trajectory JSON 里的 `final_best_score` 是 **agent 自己 CV / holdout 上的 score**，不是提交到 Kaggle 后的真实 test score。两者在 time-series / distribution-shift 任务里可能**严重 diverge**。

实例（Claude, recruit-restaurant-visitor-forecasting）：
| | NOMEM | +MEM | 结论 |
|---|---|---|---|
| agent CV RMSLE (final_best_score) | 0.517 | **0.482** ✓ | memory 更好 |
| submitted visitors mean | 20.6 | **10.8** ✗ | memory 系统性低估一半 |
| Kaggle public percentile | 66.4 | **33.8** ✗ | memory 差 32.6 pct |

原因：memory 建议的 lag_7/14/28 + reservation features 在黄金周（test 期）有大量 NaN，模型 fallback 到 bias，预测严重偏低。validation split（train 末尾）的 distribution 没捕捉到这个 regime shift。

**教训**：
1. 评估 memory / agent 效果**一律用 Kaggle percentile**，不用 trajectory 的 final_best_score
2. Time-series 任务 agent 的 validation 天然偏 optimistic（split 难保真）
3. 我们之前一直怀疑 "summary LLM 的 score 可能假" 是另一个问题，这个是独立的 "validation split ≠ test" bug
