# 2026-04-14 Cross-Task Memory: 离线构建 + 检索集成

## 动机

学生模型（baseline Qwen3-8B / SFT Qwen3-8B-v5）在 easy/hard test 上的主要失败模式是：
1. 代码运行时崩溃（sklearn API 幻觉、预处理 drop 掉 target、`n_samples=0`）
2. 错误恢复差（同一个 KeyError 19 轮都修不好）
3. 用的模型太弱（默认 RandomForest / LogReg，从不主动用 CatBoost/LightGBM/XGBoost）

Teacher 模型（Claude/GPT/Gemini/Qwen3-235B）有大量"尝试 → 改进"的成功轨迹，其中的**具体技巧**（哪个 feature 让分数从 X 涨到 Y、哪个 API 调用法修复了什么错误）可以蒸馏成 memory，运行时注入给学生。

## 2. 构建 memory entry — `scripts/build_cross_task_memory_offline.py`

### 核心思路

不为每条 trajectory 存整段代码（太长、同质化），而是只抽 **turn-level 的"有价值时刻"**：
- **improvement**：`score == best_score` 且 `best_score != prev_best_score`，即该 turn 确实建立了新 best（过滤 score=0 的幻觉值）
- **debug_fix**：`action == "debug" && not buggy`（从 bug 修到没 bug）
- **draft_success**：`action == "draft" && not buggy`，按 **25% 概率**抽样（避免过多）

Improvement 还会**回溯找 reference turn**（上一个 `score == best_score` 的 turn），把它的 plan/code/exec_output 一起传给 summarizer，让 Claude 写出 "what specific change caused X → Y"。

### Claude summarizer prompt

三种 prompt（按 entry_type 分化）：
- improvement: 对比 reference vs this turn，写 "这次做了什么让分数从 X 改进到 Y"
- debug_fix: 写"这是什么 bug，怎么修的"
- draft_success: 写"这个 draft 的关键思路值得参考什么"

所有 prompt 强调：2-3 句、<60 词、actionable、具体（不要 generic advice）、no markdown/XML。

### 过滤规则

- `success=False` 或 `final_best_score=None` → skip
- `best_turn_idx <= 1` → skip（best 太早到达，学习信号不足）
- buggy turn → skip（不从失败中学）
- score == 0.0 → skip（summary LLM 典型幻觉值）

### 产物

**`data/memory/cross_task_memory_teacher_v5.json`** — 1223 entries，11 MB

按 type 分布：
- improvement: 1016 (83%)
- draft_success: 141 (11.5%)
- debug_fix: 66 (5.4%)

按 teacher 分布：GPT 384 / Claude 363 / Gemini 340 / Coder 136（Qwen3-235B 没进，因为它的 easy 轨迹不在 distill_* 目录下）。

Cover 135 unique challenges。

Cost: ~$6（Claude Sonnet 4.6 input ~22M tokens）。

### Entry schema

```json
{
  "challenge_name": "house-prices-advanced-regression-techniques",
  "task_description": "...完整 task 描述（8K chars）...",
  "turn": 4,
  "action": "improve",
  "plan": "完整 <goal> 文本（~500 chars）",
  "model_type": "CatBoost, Ridge",  // 自动提取
  "score": 0.111,
  "score_improved": true,
  "buggy": false,
  "insight": "Blending CatBoost (0.8) with Ridge (0.2) improved OOF RMSE from 0.113 to 0.111. The combination works because Ridge captures linear residuals that CatBoost misses. Optimal blend weight was 0.60 CatBoost + 0.40 Ridge — lean more on Ridge if you see large residuals in CatBoost predictions.",
  "entry_type": "improvement",
  "teacher_model": "openai/claude-sonnet-4.6",
  "source_traj": "..._trajectory.json"
}
```

## 3. 加元数据 + 向量化 — `scripts/enrich_memory_metadata.py`

对每条 entry 加两样东西：

### (a) 结构化元数据 (Claude 分类)

给 Claude 完整 task_description，让它输出 JSON：
```json
{
  "domain": "tabular | image | text | time_series | graph | audio | multimodal | other",
  "task_type": "binary_classification | multiclass_classification | multilabel_classification | regression | ranking | segmentation | detection | generation | other",
  "metric": "rmse | rmsle | mae | auc | log_loss | f1 | accuracy | ndcg | map | other",
  "data_size": "small | medium | large"
}
```

严格 vocab 限制，parse 失败 default 到 "other"/"unknown"。

### (b) 稠密向量 (OpenAI text-embedding-3-small)

- **Task description embedding**：全文 embed（用 tiktoken 精确截到 8000 tokens，text-embedding-3-small 上限 8191）
- **❌ 不截断前 N chars**：首部 2K chars 是 marketing boilerplate（"Earthquake prediction is important..."），真正的 data fields / metric / submission format 在中后部
- **模型用 OpenAI 原生 API**（不经 LiteLLM proxy，因为 proxy 不暴露 embedding models）

### 产物

- `data/memory/cross_task_memory_teacher_v5_enriched.json` — 1223 entries + 4 新字段
- `data/memory/cross_task_memory_teacher_v5_embeddings.npy` — shape (1223, 1536), float32

分布健康：tabular 787 / text 135 / time_series 98 / image 81 / multimodal 87 / audio 15 / graph 6。task_type 里 binary_cls 424 / regression 482 / multiclass 200 等均衡。

Cost: ~$6 Claude + $0.02 OpenAI，耗时 ~4 分钟（16 worker 并发）。

## 4. Insight 向量化 — `scripts/add_insight_embeddings.py`

新加一层 embedding，对每条 entry 的 `"Goal: {plan}\n\nInsight: {insight}"` 文本 embed。

为什么：
- task_description embedding 只看 "这个 entry 是什么任务" → match 任务相似度
- insight embedding 看 "这个 entry 传达的是什么技巧" → 未来用于**匹配当前 action 需求**（turn-level dynamic query，还没实装但数据备好）

产物：`cross_task_memory_teacher_v5_insight_embeddings.npy` — shape (1223, 1536), float32，$0.02/23 秒。

## 5. 检索 — `dsgym/agents/vgs/smart_retriever.py`

### 自动启用

`AIDEAgent.__init__` 检测 `memory_path` 以 `_enriched.json` 结尾 + 同目录 `_embeddings.npy` 存在 + 两个 API key 都在 → 初始化 `SmartRetriever`，否则 fallback 到老 `CrossTaskMemory.retrieve()`（task-blind）。

必需 env：
- `LITELLM_API_KEY` — Claude 分类当前 task
- `OPENAI_API_KEY` — embed 当前 task_description

### retrieve() 流程

```
call: retrieve(current_task_description, current_action, top_k=3, pool_size=15)

┌─ Step 0: Check pool cache (keyed by hash(task_desc) + action)
│  if cached: jump to Step 6
│
├─ Step 1: Classify current task (Claude)
│  → {domain, task_type, metric, data_size}, cached per task hash
│
├─ Step 2: Embed current task_description (OpenAI)
│  → 1536-dim vector, normalized, cached
│
├─ Step 3: HARD filter entries
│  - 排除 current challenge_name
│  - entry_type 必须匹配 current action:
│      draft   → draft_success
│      improve → improvement
│      debug   → debug_fix
│  - domain 兼容（exact match 或一方是 other）
│  - task_type 兼容（同上）
│  (1223 → 通常 100-400 entries)
│
├─ Step 4: Cosine(query_emb, entry.task_desc_emb) 全向量点积
│
├─ Step 5: Top-60 by cosine → 每 challenge max 2 → 取前 pool_size=15
│  rerank: 0.8*cosine + 0.2*score_magnitude_normalized
│  (per-task cap 避免同一个 challenge 灌爆 pool)
│
├─ Step 6: random.sample(pool, top_k=3)
│  每 turn 从 cached 15 pool 里随机抽 3 条
│  → 同 task 同 action，不同 turn 会看到**不同** 3 条
│
└─ Return: List[MemoryEntry]
```

### 为什么是 "pool 15，抽 3"

- 最简 baseline。不做 MMR，不处理 negation，不用 tried_plans 动态 query。
- 同 task 同 action 多轮，**pool 稳定，每轮抽 3 条有差异**，解决 "turn 1 和 turn 5 看一模一样" 的问题
- Pool 稳定的好处：avoid agent 被频繁切换 hint 迷惑

### Format 到 prompt

注入到 user message（跟原 cross_task_memory 同位置），格式：
```
=== CROSS-TASK EXPERIENCE MEMORY ===
Here are relevant insights from similar past tasks:

[1] Task: walmart-store-sales | Action: improve | Score: 1557.3
    Insight: Adding lag-52 (same-week-last-year) ... reduced RMSE from 1633 to 1557.
[2] Task: nyc-taxi-trip-duration | Action: improve | Score: 0.395
    Insight: Log-transforming duration with log1p/expm1 combined with...
[3] Task: ...
=== END CROSS-TASK MEMORY ===
```

## 6. 安全机制 — `--no-cross-memory-write`

AIDE agent 在 online 运行时会调 `self.cross_task_memory.store_*()` append 新 entry 到 memory JSON。如果 memory 文件是**我们离线构建的 `_enriched.json`**，这会：
1. 污染 JSON（append 的新 entry 跟 embedding.npy 的对齐被打破）
2. 下次 load 会 shape mismatch

修复：新增 CLI flag `--no-cross-memory-write`。aide_agent 的三处 `store_*` 调用前加 `and not self.no_cross_memory_write`。启用 SmartRetriever 时**必须**带这个 flag。

验证：跑 eval 时对比 `stat -c %y cross_task_memory_teacher_v5_enriched.json` 的 mtime，从 eval 开始到结束**保持不变** = 写保护生效。

## 7. 效果（baseline Qwen3-8B + SmartMem vs 无 memory）

| Config | Easy Pub valid | Easy Pub %ile | Easy Priv valid | Easy Priv %ile | Hard Pub valid | Hard Pub %ile |
|---|---|---|---|---|---|---|
| no mem | 2/8 (25%) | 32.6 | 0/7 | - | 0/10 (0%) | - |
| + SmartMem | **3/8** (37.5%) | **60.6** | **2/7** (28.6%) | **67.3** | **2/10** (20%) | **41.5** |

### 关键 takeaway

- **percentile 大涨**（easy pub 32.6 → 60.6，+28；hard 从 0 → 41.5）—— 说明 "当代码跑通时，memory 让质量显著提升"
- **valid rate 微弱提升**（+1，+2）—— memory 没救 "代码崩在 to_csv 之前" 的核心 bug
- **对比 teacher ceiling**：Qwen3-235B 在 easy pub %ile 58.8（valid 5/8）→ baseline + SmartMem **60.6**（valid 3/8）——**在 valid 的任务里，memory 把 8B 抹平到 235B 水平**
- memory 影响 goal 内容显著：CatBoost 提及 46 次、XGBoost 23、LightGBM 21（总 68% goal mention GBDT），明显超过 baseline 的 sklearn 默认倾向

## 8. 没做 / 未来方向

下面是讨论过但**明确选择先不做**的优化（保持 baseline 简单）：

1. **Turn-level 动态 query**：insight_embeddings.npy 已备好，但目前只用 task_desc embedding。未来可以让 action_hint 随 turn 变化（例如 debug 用 last error、improve 用 "recent tried plans" + best），然后用 `0.5*cos(task_desc) + 0.5*cos(insight, action_hint)` 打分，每轮召回不一样。
2. **MMR penalty**：对 "已经尝试过的 plan" 显式 penalize 相似 entry（处理 embedding 对 negation 不敏感的问题）。
3. **补 hard_test teacher benchmark**：闭源 3 家 teacher（Claude/GPT/Gemini）的 `_hard_train` 只跑了 train 44 个，没 cover hard_test 10 个。要 ceiling 对比需要重跑。
4. **修 final_submission prompt**：当前只传 summary_section，没传 best turn 完整代码。模型从 summary 重建 pipeline 常常漏关键步骤导致崩。
