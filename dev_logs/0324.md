# Dev Log 2026-03-24: Memory V4 — LLM-Generated Turn Summaries

## 一、前情回顾：V2/V3 遗留问题

Memory V2 是当前最佳配置（mean percentile 48.83），但存在两个结构性问题：

### 问题 1: good_nodes 分数不准

AIDE 的 task 内记忆（`good_nodes`）存储的是每轮的 plan + score，用于 Improve 时选择最优方案。但 score 来源有 bug：

| 尝试 | 方案 | 结果 |
|---|---|---|
| V1 原始 | 存 `best_score`（模型在 `<search_state>` 中自报的累计最优） | 所有 node 分数一样——`best_score` 是全局最优，不是当前轮实际得分 |
| V2 修正 | 从 execution output 正则提取 `Validation Score: xxx` | 98.2% 匹配率，但取错了行——部分 case 取了 std 而非 mean，导致 88% 的 score 和模型自报值不一致 |
| V3 尝试 | 在 `<search_state>` 中加 `<current_score>` 让模型自报当前轮分数 | 失败——模型在生成代码 **之前** 就填了 `<current_score>`，这时代码还没执行，填的是预测值或空 |

**根因**：score 必须在代码执行 **之后** 获取，但模型的 response（包含 `<search_state>` 和 `<python>`）是在执行之前生成的。正则从 execution output 提取又不可靠（格式不统一、取错行）。

### 问题 2: cross-task memory 写入时机错误

`store_improvement()` 在检测到 score 提升时触发，但写入的是 **当前轮** 的 plan/code。问题在于：

- 当前轮的代码可能还没执行完就触发了（如果 score 检测逻辑有延迟）
- 更严重的是：score 提升的检测本身就依赖于上面有 bug 的 score 提取

### 问题 3: best-node 策略失败

`--best-node-strategy best` 本意是让 Improve 从分数最高的 node 出发（而非最新的），更接近原版 AIDE 的树搜索。但实验结果 **更差**（mean -3.7），因为：

- `best_score`（模型自报）和 `good_nodes` 的 `current_score`（正则提取）不一致
- `_get_best_approach_summary()` 用 `score == best_score` 匹配，经常找不到，fallback 到错误的 node
- 且 `max(scored, key=lambda e: e["score"])` 假设越大越好，但部分 metric 是越小越好（RMSE, log_loss）

## 二、Memory V4 设计

核心思路：**在每轮代码执行之后，单独调一次 LLM 来生成结构化总结**。

这解决了所有上述问题：
1. **Score 准确**：LLM 看到完整的 execution output 后再提取分数，不依赖正则
2. **时机正确**：总结在代码执行完毕后生成，写入的是已确认的结果
3. **Metric 方向由模型判断**：模型自己跟踪 `best_score`，知道是越大越好还是越小越好

### 架构变化

```
V2/V3:
  模型 response → 执行代码 → 正则提取 score → 条件性写入 memory
                              ↑ 不可靠

V4:
  模型 response → 执行代码 → 调 LLM 总结 → 写入 task_memory + 条件性写入 cross_task_memory
                              ↑ 看到完整 exec output
```

### 两种 Memory 的分工

| | Task 内 Memory | Cross-Task Memory |
|---|---|---|
| 作用域 | 当前 task | 跨 task |
| 存储位置 | 内存中的 list | JSON 文件（持久化） |
| 写入时机 | 每轮都写 | 只在高价值事件时写 |
| 内容 | step, model, score, best_score, notes | type, model, insight |
| 注入位置 | 每轮 prompt 的 memory_section | 每轮 prompt 的 memory_section（追加） |

### Summary Prompt 设计

每轮执行完后，用以下 prompt 调 LLM（独立的单轮对话，不污染主对话）：

**输入**：
- 截至当前的所有 task 内 memory（让模型知道之前的尝试和分数）
- 上一轮的 execution output（上下文连续性）
- 当前轮的 step / action / plan
- 当前轮的 execution output（关键——包含实际分数）

**输出**（XML 格式）：

```xml
<task_memory>
  <step>5</step>
  <model>LightGBM</model>
  <score>0.1384</score>
  <best_score>0.1384</best_score>
  <notes>Switched from CatBoost to LightGBM with target encoding, improved from 0.1526</notes>
</task_memory>

<!-- 仅在分数提升或 debug 成功时 -->
<cross_task_memory>
  <type>improvement</type>
  <model>LightGBM</model>
  <insight>LightGBM with target encoding outperforms CatBoost on this regression task</insight>
</cross_task_memory>
```

**不输入 code**：代码在 conversation 里，summary LLM 不需要看——它只需要从 execution output 中提取结果。

### Cross-Task Memory 写入条件

由 LLM 判断是否值得写入，prompt 指导只在两种情况下生成 `<cross_task_memory>`：
1. **improvement**：本轮分数超过了之前的 best_score
2. **debug_fix**：本轮成功修复了上一轮的 bug

任务结束时，额外调 `store_task_summary()`（代码逻辑，非 LLM 判断）。

### Best-Node 策略修复

每个 task_memory entry 现在有 `best_score` 字段（模型判断的截至当前的累计最优）。

- **strategy=latest**：取 `scored[-1]`，最近一个有 score 的 entry
- **strategy=best**：从最新 entry 的 `best_score` 反查，找 `score == best_score` 的 entry。**模型自己处理了 metric 方向**，不再需要我们假设越大/越小越好

```python
if strategy == "best":
    # 取最新的 best_score
    latest_best = None
    for e in reversed(task_memory):
        if e.get("best_score") is not None:
            latest_best = e["best_score"]
            break
    # 反查哪个 entry 的 score 等于 best_score
    if latest_best is not None:
        for e in reversed(scored):
            if abs(e["score"] - latest_best) < 1e-9:
                return e
```

### 每轮 Prompt 注入内容

| 内容 | draft | improve | debug | final_submission |
|---|---|---|---|---|
| task 内 memory | ✅ | ✅ | ✅ | ✅ |
| cross-task memory | ✅（除非 `--no-draft-memory`） | ✅ | ✅ | ✅ |
| reference approach (best/latest) | ❌ | ✅ | ❌ | ❌ |

Improve 时注入 reference approach 示例：
```
--- Reference approach (best scored) ---
Step 3 | Model: LightGBM | Score: 0.1384 | Switched to LightGBM with target encoding
--- End reference ---
```

### Task 内 Memory 展示格式

```
=== TASK MEMORY (Previous Attempts) ===
Step 1 | Model: CatBoost | Score: 0.1526 | Best so far: 0.1526 | Baseline CatBoost with default params
Step 2 | Model: CatBoost | Score: 0.1498 | Best so far: 0.1498 | Added target encoding for categorical features
Step 3 | Model: LightGBM | Score: 0.1384 | Best so far: 0.1384 | Switched to LightGBM, significant improvement
Step 4 | Model: LightGBM | Score: error | Best so far: 0.1384 | Tried adding polynomial features, OOM error
=== END TASK MEMORY ===
```

## 三、日志输出

每轮打印三条信息：

```
  [TaskMemory] step=3, model=LightGBM, score=0.1384, best_score=0.1384, notes=Switched to LightGBM...
  [CrossTaskMemory] type=improvement, model=LightGBM, insight=LightGBM with target encoding outperforms...
  Turn 3: action=improve, buggy=False, score=0.1384, drafts=5, task_memory_size=3, node_strategy=best
```

Trajectory JSON 新增字段：
- `task_memory`: 完整的 task 内 memory 列表
- `best_node_strategy`: "latest" 或 "best"
